# Phase 3.1: Hardware Abstraction Layer (HAL) Architecture

## 1. Purpose
Establish the boundary between high-level Python application/DSP logic and hardware-specific physical peripherals (e.g. ESP32-S3 I2S, DMA, GPIO). This enables strict software-in-the-loop simulation while preparing a clean contract for future C/C++ embedded drivers.

## 2. HAL Boundary & Layer Diagram
```
[ APPLICATION / XIAOZHI ]
           │
[ SERVICES (Voice/Vision) ]
           │
[ FROZEN DSP PIPELINE ]
           │
====================================== <-- HAL BOUNDARY
[ HARDWARE ABSTRACTION LAYER (HAL) ]
======================================
           │
[ PHYSICAL HARDWARE (ESP-IDF Drivers) ]
```
The higher layers are absolutely prohibited from touching hardware registers, DMA descriptors, or `esp_err_t`. All errors and states must use `HALError` and `HALState` enums.

## 3. Audio Frame Contract & Format Boundary
The audio pipeline is structured around 16 kHz, 16-bit signed Mono PCM. However, the data representation crosses multiple boundaries.

### A. Hardware Transport Representation
- **Hardware PCM**: 16-bit signed integer (`int16_t`) PCM at 16 kHz. This is the exact format generated by the I2S microphone and consumed by the I2S speaker.

### B. HAL Representation
- **AudioCaptureFrame** / **AudioPlaybackFrame**: Abstract classes holding the audio frame alongside `timestamp` and `seq_num`.
- **Internal Conversion**: The Python HAL implementation accepts and stores Python `float` lists to interface smoothly with the simulation. When ported to C++, the HAL implementation will handle the conversion of `int16_t` hardware DMA buffers to the `float32_t` arrays required by the DSP boundary.

### C. DSP Internal Representation
- The frozen Phase 2 DSP exclusively utilizes arrays of Python floating-point numbers (`float`) representing standard continuous variables for its filtering mathematics. The HAL is fully responsible for providing these floats.

## 4. Capture & Playback Paths
- **Capture**: The microphone DMA fills buffers in hardware, pushing them into the HAL, which generates `AudioCaptureFrame`s.
- **Playback**: The application pushes `AudioPlaybackFrame`s into the HAL, which routes them to the speaker I2S DMA.

## 5. AEC Reference Association vs Synchronization
**CRITICAL DISTINCTION:**
The HAL provides **Frame Association** metadata (via sequence numbers and timestamps). The `read_reference_frame()` method allows the AEC to request the specific playback frame that corresponds logically to a given point in time.

The abstract HAL does **NOT** guarantee physical acoustic synchronization.
Physical synchronization remains deferred to the hardware-validation phase and depends heavily on:
- I2S TX/RX timing
- DMA scheduling
- Speaker playback latency
- Microphone capture latency
- Acoustic propagation in the physical casing
- Clock behavior

## 6. Buffer Ownership
- **Producer**: The hardware DMA produces raw PCM; the HAL adapter produces `AudioCaptureFrame`s.
- **Consumer**: The DSP pipeline consumes the frames. 
- **Lifetime**: Once read via `read_capture_frame()`, ownership of the logical data transfers to the DSP.
- **Errors**: `BUFFER_UNAVAILABLE` (Underrun) or `OVERRUN` are returned natively if queues mismatch.

## 7. Lifecycle & State Machine
The HAL implements a deterministic state machine:
`UNINITIALIZED -> INITIALIZED <-> RUNNING -> STOPPED -> DEINITIALIZED`
Invalid transitions (e.g., stopping while uninitialized, deinitializing while running) yield a deterministically defined `HALError.INVALID_STATE_TRANSITION` or `HALError.NOT_INITIALIZED`.

## 8. Error Model
A uniform, hardware-independent Enum:
- `OK`, `NOT_INITIALIZED`, `DEVICE_UNAVAILABLE`, `INVALID_CONFIGURATION`, `BUFFER_UNAVAILABLE`, `OVERRUN`, `UNDERRUN`, `TIMEOUT`, `HARDWARE_ERROR`, `INVALID_STATE_TRANSITION`.

## 9. Mock Testing Strategy
The architecture relies entirely on `AudioHAL` Python mocks that enforce interface constraints and state machine rules. No physical hardware execution takes place. 

## 10. Hardware Implementation Deferred Items
- Physical ESP32 I2S Peripheral Initialization
- C++ `esp-dsp` integration
- Translating Python lists to contiguous C-arrays.
- Validating real acoustic alignment.

## 11. Relationship to Frozen Phase 2 DSP
The HAL wraps cleanly beneath Phase 2. `AudioCaptureFrame.pcm_data` maps directly to Phase 2's `AudioBuffer`. No Phase 2 components were modified or refactored to support this architecture.
